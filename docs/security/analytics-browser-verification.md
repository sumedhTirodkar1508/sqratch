# Analytics browser verification — 2026-10-31

A local production build was tested in headless Chrome using an unreachable loopback database, synthetic credentials and synthetic URLs. The browser used a process-scoped loopback proxy that served downloaded official Google and Vercel SDKs and returned 204 for all other external requests. Vercel collection endpoints were intercepted locally. No collection request in the proxy-backed runs reached a provider. No database writes or provider actions were performed. Chrome's automation flag and headless user agent were masked for Vercel tests because the hosted scripts otherwise deliberately exit without sending telemetry.

## Results

- **Google delivery failed in the tested iframe setup.** The official public-property-configured SDK executed in the opaque sandbox and processed the configuration and page-view commands, but no collection request appeared. A direct, no-frame control on a clean synthetic loopback page using the same official SDK and public measurement ID did produce a locally blocked page-view collection request. An additional same-origin frame comparison also produced no collection request; this does not establish that cookie denial alone causes the failure. The proxy was offline and the control used synthetic content. GA delivery remains a rollout blocker pending a provider-compatible solution that preserves the security boundary and representative validation.
- Follow-up controls used the same configured official SDK, explicit synthetic client ID, and disabled advertising signals. The direct no-frame control emitted a locally blocked page view. Serving the opaque iframe from a real loopback HTTP URL instead of `srcdoc` did not produce a collection request; nor did explicitly denying analytics and advertising storage before configuration. Neither experiment identifies the cause or justifies relaxing the sandbox.
- Actual Next.js links navigated synthetic login → signup → public home: the sensitive pages had no analytics frame or collection, and public home resumed its frame and sanitized Vercel view. Browser Back traversed public → signup → login with the frame removed and no sensitive collection; Forward restored public telemetry. No public-to-sensitive Next Link was present on the tested public pages, so the reverse transition was exercised with browser history.
- The Google iframe used `sandbox="allow-scripts"` and `referrerpolicy="no-referrer"`; the SDK script request had no Referer header. Its sandboxed document's cookie getter raised a SecurityError, as expected. Google did not expose a console or page error in this test.
- Sensitive hard loads for synthetic Commerce7 connect, Commerce7 link (redirected to login), nested login callback, and verify-email did not initialize analytics. The Commerce7 script request was locally blocked. Tested responses had `Referrer-Policy: no-referrer`.
- The official Vercel Web Analytics SDK emitted a locally blocked `/about` view with the query and fragment removed. The official Speed Insights SDK emitted locally blocked static `/about` vitals with sanitized URL and route. Its actual payload included a CSS selector in `attribution.eventTarget`: the hosted SDK preserves attribution and its original route outside the `beforeSend` return value. This discovery prompted the additional restriction of Speed Insights to reviewed static routes.
- After that change, a synthetic dynamic `/x/...` hard load emitted no dynamic performance payload. A late `/about` vital emitted during navigation contained only the prior static context. The dynamic route did not mount a Google frame in the unreachable-database fixture, so this observation does not validate a fully rendered experience or dynamic SPA transition.

## Limits and artifacts

The first exploratory Chrome run exposed a Playwright interception blind spot: requests from the opaque frame bypassed the context route and the real Google SDK loaded. Only the synthetic measurement ID and synthetic test URLs were used; no collection request was visible to that interceptor, so its network outcome cannot be asserted. All later SDK and collection tests used the deny-by-default local proxy, which observed the iframe request. The proxy made no outbound connections. The configured production measurement ID was public page configuration; collection was blocked locally.

Temporary evidence is in `/private/tmp/sqratch-proxy.log`, `/private/tmp/sqratch-ga-control.log`, `/private/tmp/sqratch-real-proxy-all.log`, `/private/tmp/sqratch-control-proxy-all.log`, and `/private/tmp/sqratch-updated-vitals.log`. These are local test artifacts, not production HARs. They may be removed by the operating system. The test harnesses and downloaded SDKs are also under `/private/tmp/sqratch-*`.

Authenticated Commerce7, Shopify, provider sandbox flows, valid database-backed dynamic experiences, real property receipt, and fully rendered dynamic SPA navigation were not tested. A real staging environment was unavailable. Existing automated tests cover policy and lifecycle cases but do not replace those browser acceptance checks.

## Follow-up: server-side Measurement Protocol — 2026-11-10

The iframe experiment above describes the superseded implementation. The current implementation sends reviewed events to a same-origin endpoint, which constructs the Measurement Protocol request server-side. A local production build used synthetic configuration and an unreachable database. A process-scoped test preloader intercepted the server's Google request and returned a synthetic 204; a loopback proxy blocked external browser requests. This verifies local dispatch and request construction, not Google's acceptance or reporting. No configured test property credentials or Realtime result were available.

An initial production-browser run returned 403 even for a same-origin request. The browser sent the expected loopback Origin and Host with `Sec-Fetch-Site: same-origin`; the reason for the initial server mismatch was not instrumented. After changing the check to use the configured canonical origin, the rebuilt application passed:

- Loading `/about?token=SYNTHETIC_QUERY#SYNTHETIC_FRAGMENT` sent a page-view event to the local endpoint, which returned 204. The intercepted server payload used `/about` and contained no query or fragment.
- A synthetic approved `product_click` for the campaign route returned 204. The server payload preserved the reviewed numeric and currency fields and used `/c/[campaignSlug]`. A raw dynamic path and an email property each returned 400 and generated no server delivery.
- Synthetic login → signup → public home via Next links, then browser Back and Forward, generated no sensitive-route telemetry; public home page views resumed. The browser sent no Google iframe requests.
- `/favicon.ico` returned 200 with 10,557 bytes. Its 16×16, 32×32, and 48×48 frames are the original embedded frames from the supplied new icon. The backup remained byte-identical to the previous Git favicon.

The local server and proxy were stopped after the test. A dedicated property and authorized staging Realtime or DebugView check remain necessary to establish provider receipt. Synthetic capture artifacts, without the API secret in the captured endpoint, are `/private/tmp/sqratch-mp-browser-final.log` and `/private/tmp/sqratch-mp-server-capture.log`.
